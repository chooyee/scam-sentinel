Scam Sentinel · developer guide

How Scam Sentinel works

A tour of the code for developers: how transfers become numbers, how a 9,121-parameter Transformer reads them, how a score is explained, and how the public IBM AML dataset is turned into training data.

01The idea

In an authorised-push-payment (APP) scam the victim is talked into sending money themselves. The login, device and location are all genuine, so classic fraud signals stay quiet. Two clues are left:

1. The payment breaks the account's pattern

Bigger than usual, to a new payee, at an odd hour, draining the balance, in a burst of top-ups.

2. The receiver looks like a mule

Many unrelated senders paying in, money forwarded on within minutes, split into equal slices or cashed out through e-wallets and crypto.

Scam Sentinel treats an account's 14 most recent transfers like the words of a sentence and asks a small Transformer whether the last one "fits the story". Everything happens in the browser: no server, no data leaves the page.

02Run it

npm start                 # node tools/serve.js, localhost:8080 only
npm run check             # syntax + data-shape checks (also runs in CI)
npm run data:download     # ~450 MB IBM AML raw files into data/ (git-ignored)
npm run data:convert      # rebuild training-data/ibm-aml-corpus.*

You can also double-click scam-sentinel.html. Serving it is only needed for Load from path and the ?corpus= URL parameter, because browsers block fetch() from file:// pages. There is no npm install: the page uses TensorFlow.js 4.22.0 from cdnjs and the tools use only the Node standard library.

04Data: transfers and timelines

The unit of training data is a timeline: one account's 14 most recent transfers, oldest first, plus a label for the newest one.

{ id, label: 0 | 1, scenario, ownerTypicalAmount, transfers: Transfer[14] }

A Transfer carries raw fields about the payment (amount, direction, hour, gap, new payee, drain), about the receiver (account age, fan-in 1 h / 24 h / 7 d, fan-out 1 h / 24 h, pass-through, three onward-flow shares), and two derived fields (amountVsTypical, isRoundAmount). createTransfer() fills in the derived ones.

The synthetic generator

Each timeline starts from a random account profile (typical amount RM 30–800, balance RM 2k–60k, an active hour, 2–4 known payees), fills 14 normal transfers, then optionally rewrites the tail.

KindTailWhy it exists
routinenonebaseline behaviour
big new payee (25% of legit)one genuine RM 5k–40k payment to a new, clean payeehard negative: stops the model learning "new payee + big = scam"
investment4 escalating round top-ups to the same mulescam scenarios; every tail pays a receiver with a mule signature (high fan-in and fan-out, pass-through 0.7–1.0, young account)
impersonation1 transfer of 60–95% of the balance, off-hours
job / tasksmall inbound "commissions" alternating with outbound "deposits"
purchase1–2 modest payments

Load a receiver-signature library (see section 09) and the generator samples receiver-side fields from real-shaped snapshots instead of the fixed ranges.

Importing data

importCorpusText() accepts the CSV (one row per transfer) or JSON layout in TRAINING-DATA-GUIDE.md. It groups rows by account_id, orders them, keeps the last 14, left-pads short histories, derives hour and gap from timestamps, applies defaults, and rejects accounts with invalid values, listing the reason. A file whose format is scam-sentinel-mule-signatures is routed to applySignatureLibrary() instead.

Point-in-time rule. Every receiver feature must be computed from data available at the transfer's timestamp. Computing fan-in with data that arrived later leaks the future: the model looks brilliant in training and fails in production.

06The model

A single-block Transformer encoder with attention pooling, written with raw tf.variables (no Keras layers) so every step is visible in forwardPass().

  1. Project. Lift 19 features to MODEL_DIM = 32 and add sinusoidal position encoding, so the model knows which transfer is the newest.
  2. Self-attention. Each transfer builds a query, key and value; softmax(QKᵀ/√32) decides how much each transfer borrows from the others. This is where "four top-ups to the same kind of receiver in a row" becomes visible.
  3. Feed-forward. A small per-position MLP, with a residual connection and LayerNorm around each sub-layer.
  4. Attention pooling. A learned score per position, softmaxed over the 14 positions, gives a weighted average: one vector per timeline.
  5. Classify. Dense to one logit, sigmoid to a probability.

08Scoring and explanation

The score form describes one transfer. scoreTransfer() appends it to a fixed background of 13 identical routine transfers (RM 300, 14:00, one day apart, known payee), so the score depends only on the form inputs and is fully repeatable.

< 0.33Fits the story: let it through
0.33 – 0.66Out of pattern: warn, confirm payee
≥ 0.66Likely mule: hold, cool off, verify

Occlusion explanation

Each of the 14 positions is swapped in turn for a benign baseline row and the timeline is re-scored. The drop in probability becomes a bar in the explanation strip: tall, warm bars are the transfers that pushed the score up. It costs 14 extra forward passes, which is nothing at this model size.

Embedding view

Held-out timelines are run with returnEmbedding: true; the 32-d pooled vectors are reduced to 2D with PCA (power iteration, one deflation) in projectTo2D() and plotted as legit vs scam.

09The IBM AML converter

No public dataset has labelled APP scam transfers. tools/ibm-aml-to-scam-sentinel.js converts IBM's synthetic Transactions for Anti Money Laundering dataset, which has a full account graph and labelled laundering typologies, into the Scam Sentinel layout.

  • Owner = sender of the anchor transfer; timeline = the owner's last 14 transactions up to the anchor.
  • Label 1 = the anchor is flagged Is Laundering (its typology becomes the scenario, e.g. aml:fan-in). Label 0 = a clean anchor from an owner who never touches a laundering row; 25% of these are "big new payee" hard negatives.
  • Amounts are converted to MYR with a static FX table. Fan-in, fan-out, pass-through and onward shares are computed for the counterparty in trailing windows. Receiver account age is not in the dataset and is left blank.
  • Output is deterministic for a given --seed: re-running npm run data:convert reproduces the committed files byte for byte.

The signature library is often the more useful output: load it into the page and synthetic victims start paying receivers whose behaviour is drawn from real-shaped laundering and clean snapshots.

Laundering is not APP scam: in IBM's data the owner is the launderer, not a victim. Treat the converted corpus as a pipeline test, not an accuracy benchmark. Measured held-out AUC on it is about 0.94, against 1.00 on synthetic data, which says more about synthetic data than about the model.

10Extending the code

Add a feature

  1. Add the raw field to createTransfer() with a default, and set it in the generator functions in §3.
  2. Append its encoding to encodeTransfer() and bump FEATURES_PER_TRANSFER.
  3. Add it to IMPORT_COLUMNS / EXPORT_FIELDS (and IMPORT_RATIOS if it is 0–1), the editor columns, the score form and SCORE_PRESETS.
  4. Update the template CSV, example JSON, schema, TRAINING-DATA-GUIDE.md and SPEC.md; if the IBM converter can compute it, add it there too.

Add a scam scenario

Add a branch to createScamSequence() that overwrites the last few transfers using createTransferToMule(), add its label to SCENARIO_LABELS, and include it in the weighted scenario list.

Change the model

Weights live in buildModel(), the computation in forwardPass(). Keep the returnEmbedding option working, since the embedding view depends on it. Ideas from the backlog: an attention mask for padded rows, multiple heads, returning pooling weights for a cheaper explanation.

The prioritised backlog of bugs, accessibility fixes and features is in VALIDATION-REPORT.md.

11Limitations

  • Synthetic data separates far more cleanly than real traffic; the accuracy shown in the page is not indicative.
  • One bank sees only its own senders; real fan-in and pass-through need cross-bank intelligence.
  • The model has no notion of receiver identity: "same mule four times" is only visible through a repeated signature.
  • No attention mask, so padded rows count as real history.
  • Corpus generation and the train split use unseeded Math.random(), so in-page results vary run to run.
